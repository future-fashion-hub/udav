# Бэкенд УДАВ на Go: контракт реализации v1

Это техническое задание для будущего сервера, а не описание уже подключённой функциональности. Сейчас native/App.tsx хранит профиль, очки, витрину и историю в React state; соперник увеличивает прогресс по таймеру. После интеграции этот таймер и локальное начисление очков удалить. Browser src/Prototype.tsx должен использовать тот же API.

## Архитектура и запуск

Один Go-сервис: HTTP REST + WebSocket, PostgreSQL как источник постоянных данных, объектное S3-совместимое хранилище + CDN для картинок. Redis нужен при нескольких экземплярах для присутствия, ограничителей и поиска владельца комнаты. Для MVP комнаты обслуживает один процесс; нельзя распределять одну комнату между независимыми циклами.

Каталоги: cmd/api, internal/auth, users, catalog, battles, realtime, storage; migrations, api/openapi.yaml, api/asyncapi.yaml. Предоставить Dockerfile, compose.yaml (api/Postgres/Redis/локальное S3), .env.example без ключей, миграции и команду seed. Переменные: DATABASE_URL, REDIS_URL, S3_ENDPOINT/BUCKET, CDN_BASE_URL, TOKEN_SIGNING_KEY, ALLOWED_ORIGINS, PORT. Секреты — в окружении, не в Git. /health/live проверяет процесс, /health/ready — БД и готовность принимать комнаты. Graceful shutdown прекращает новые матчи и завершает/сохраняет текущие.

## Данные

Время хранить UTC RFC3339, UUID для сущностей; очки и проценты передавать числами, форматировать на клиенте.

- users: id, name (1–24 символа), bio (до 100), avatar_asset_id, rating (>=0, начальное 1240 для совместимости демо), created_at, version.
- sessions: user_id, refresh_token_hash, expires_at, revoked_at; ротация refresh с обнаружением повторного использования.
- assets: id, sha256, mime, width, height, original_key, bytes, version. Разрешённые типы PNG/WebP/JPEG; проверять фактический формат и размеры.
- achievements: стабильный строковый id, name, description, asset_id, rule_code, rule_version, enabled. Исходные названия/условия взять из native/achievements.ts. Индекс массива НЕ использовать как серверный ID; сделать явную таблицу соответствия art → id.
- user_achievements: user_id, achievement_id, unlocked_at, evidence_battle_id; UNIQUE(user_id, achievement_id).
- showcase: user_id, slot (1..3), achievement_id; уникальные slot и achievement в пределах пользователя. Сервер разрешает только разблокированные достижения.
- friendships: пара пользователей, статус pending/accepted/blocked; invite_codes: owner_id, code_hash, expiry.
- battles: id, player_a/b, status, rules_version, started_at, finished_at, winner_id, finish_reason, version.
- battle_results: battle_id, user_id, rating_before/after, delta; UNIQUE(battle_id,user_id). Отдельная таблица результатов/участников допускает один результат на участника.

История и счётчики выводятся из завершённых матчей. Победа +25, поражение -15, rating=max(0,rating+delta); delta в истории — фактическое изменение. При ничьей и отмене без старта delta=0. Демо-историю не переносить новым реальным аккаунтам. Правила автоматической выдачи достижений согласовать отдельно: текущие описания ещё не являются кодом выдачи.

## REST /v1

Все приватные запросы: Authorization: Bearer <access_token>. TLS обязателен. Ответ ошибки: {"error":{"code":"SHOWCASE_LIMIT","message":"На витрине только 3 места","requestId":"uuid"}}. Коды HTTP: 400 входные данные, 401 сессия, 403 запрет, 404 отсутствует, 409 конфликт версии/состояния, 429 лимит с Retry-After. Ограничить тело запроса и длины строк.

| Метод | Путь | Назначение |
|---|---|---|
| POST | /auth/guest | Создать гостевую учётку и сессию; позже привязать выбранный способ входа. Установка не доказывает уникальность человека |
| POST | /auth/refresh | Ротация refresh; выдача короткого access |
| POST | /auth/logout | Отозвать сессию |
| GET/PATCH | /me | Профиль, rating, wins/losses/battles; PATCH только name/bio/avatarAssetId, с version |
| GET | /users/{id} | Публичный профиль, статистика, витрина |
| GET | /catalog?locale=ru | Версия каталога, тексты и метаданные изображений; ETag/If-None-Match |
| GET | /me/achievements | Выданные достижения |
| PUT | /me/showcase | {"achievementIds":["cowboy", "shock"],"version":3}; атомарная проверка <=3, без дублей |
| GET | /leaderboard?cursor=...&limit=20 | Стабильный порядок rating DESC, id ASC; своё место отдельным полем |
| GET | /me/battles?cursor=...&limit=20 | История, соперник, результат, delta, finishedAt |
| POST | /invites | Выдать ограниченный по сроку код |
| POST | /friends/accept-code | Принять код, запретить себя, дубли и блокировки |
| GET | /friends | Друзья и доступность; не выдавать точную геопозицию |
| POST | /battles | {"opponentId":"uuid"}; создать приглашение с TTL 30 секунд |
| POST | /battles/{id}/accept | Принять приглашение; повтор безопасен |
| POST | /battles/{id}/decline | Отклонить |
| GET | /battles/{id} | Авторитетный snapshot для участников |
| POST | /realtime-ticket | Одноразовый билет WebSocket, TTL 30 секунд |

POST создания/accept/decline и PUT витрины поддерживают Idempotency-Key с хранением результата (24 часа) в области user+route. Повтор с иным телом — 409. Игрок одновременно участвует только в одном активном матче. Поиск «рядом» пока заменить списком друзей/онлайн: реальную геолокацию включать только после отдельного продуктового решения и согласия пользователя.

Пример элемента каталога:
```json
{"id":"cowboy","name":"Самый быстрый трясун дикого запада","description":"...","image":{"url":"https://cdn.example/assets/<sha>.png","width":1024,"height":1024,"sha256":"..."}}
```

## Изображения и тексты без потери качества

Оригиналы из public/assets/udav хранить побайтово неизменными. Не делать JPEG из прозрачных стикеров, не снижать разрешение или качество. Адрес содержит хеш; Cache-Control: public,max-age=31536000,immutable. Новая картинка получает новый URL. Тексты и ссылки отдаёт версионированный каталог с ETag. Байты PNG не пересылать внутри JSON/WebSocket. На клиенте дисковый кеш, явные размеры, виртуализация списка и ограниченная предзагрузка соседних строк. При отключённой сети использовать последний валидный каталог и локальные оригиналы. Серверное хранение уменьшит размер APK лишь после отдельной миграции require(...) на удалённые URI; сам сервер не исправляет декодирование всех картинок одновременно.

## Real-time протокол

Подключение wss://api.example/v1/realtime?ticket=<one-time-ticket>. Билет погашать атомарно; query не писать в access logs. До авторизации события запрещены. Для браузера проверять Origin по allowlist, native без Origin допускать только с билетом. Авторизованный userId брать из сессии, никогда из тела события.

Конверт клиента: {"v":1,"type":"battle.strokes","id":"uuid","battleId":"uuid","seq":12,"payload":{...}}. Сервер: {"v":1,"type":"battle.state","battleId":"uuid","serverSeq":44,"serverTime":"RFC3339","payload":{...}}. seq монотонный для участника матча; дубликаты отбрасывать, ack включает lastAcceptedClientSeq. Размер сообщения <=16 KB, лимит 20 игровых сообщений/сек/игрок; конечные числа и допустимые поля проверять.

События клиента: battle.ready, battle.strokes, battle.leave, battle.resume, ping. Сервер: invite.created/expired/declined, battle.countdown, battle.started, battle.state, battle.finished, error, pong. Обе стороны должны подтвердить ready; сервер назначает startsAt не раньше чем через 3 секунды. До startsAt движения не учитываются. Снимок содержит phase, startsAt, rulesVersion, players[{userId,progress}], lastAcceptedClientSeq, deadline и финальный result при завершении.

Сырые датчики остаются на устройстве (50 ms как сейчас). Native отправляет пачки распознанных смен направления каждые 100 ms, а не каждый кадр UI. payload: {"strokes":[{"n":37,"elapsedMs":12050,"direction":1}]}; n непрерывный номер удара в матче, direction ±1, elapsedMs от серверного startsAt с поправкой смещения часов. Пустая пачка допустима. Сервер ограничивает длительность пачки 200 ms, число ударов и их частоту по согласованному rulesVersion, отбрасывает повторы n и старые пачки; не принимает clientProgress, winner или rating. Монотонное серверное время определяет фактический прогресс/убывание; клиентские timestamps используются только как ограниченная проверка правдоподобности, без перемотки завершённого матча.

Перенести численные правила из native/battle-motion.ts (stroke detector/decay) в версионированный rules fixture; шаг +7 как в App.tsx, grace/decay брать из функции, не придумывать второй набор. Минимальный интервал ударов и допустимые отклонения часов зафиксировать вместе с тестовыми записями реального датчика до релиза. Серверный тик 50 ms, рассылка snapshot каждые 100 ms; визуально клиент интерполирует, но сверяет с snapshot. Предсказание допускается только для своей шкалы и откатывается по ack. Убывание обоих игроков рассчитывает сервер даже при молчании клиента.

Каждая комната — одна goroutine с входным каналом и единственным владельцем состояния. Первый достигший 100 на серверной временной шкале побеждает; если оба достигли на одном тике — ничья (0 очков), без зависимости от порядка обхода игроков. Максимум матча 120 секунд; по таймауту выше progress — победитель, равные — ничья. Точные продуктовые значения вынести в rulesVersion и согласовать до запуска. Добровольный выход после старта — поражение; до старта — отмена без очков. Повторный leave не меняет результат.

Доверять сенсорам полностью нельзя: модифицированный APK умеет подделывать движения. Лимиты и анализ последовательностей снижают злоупотребления, но не доказывают физическую тряску. Для соревновательных наград отдельно решить необходимость аттестации устройства и более подробной телеметрии.

## Разрыв соединения и фиксация результата

Heartbeat каждые 10 секунд; считать соединение потерянным после 30 секунд без pong. После обнаружения дать 10 секунд на возврат. Убывание идёт, второму участнику отправляется connectionStatus. Клиент переподключается с backoff 0.5/1/2/4/8 секунд + jitter, получает новый билет, отправляет battle.resume с lastServerSeq. Сервер отвечает полным snapshot; старые движения повторно не применяет. По истечении grace отсутствующий проигрывает, оба отсутствуют — отмена без очков. Если матч уже закончен, вернуть сохранённый result.

Финал одной транзакцией: заблокировать battle и строки обоих users в стабильном порядке; проверить status=active; сохранить результат, rating, статистику и достижения; записать outbox-событие; commit; затем broadcast. UNIQUE результатов защищает от повторного начисления. При конфликте вернуть уже записанный результат. Outbox отправлять с повторами, клиенты дедуплицируют serverSeq/resultId.

Для нескольких серверов владелец комнаты имеет lease с fencing token. После потери lease процесс прекращает вычисления; PostgreSQL проверяет token при commit. Нельзя запускать две авторитетные комнаты. При перезапуске MVP активные матчи помечаются interrupted и отменяются без очков; результаты уже завершённых не менять. Клиент после reconnect получает это состояние. Позже можно добавить периодические snapshots и восстановление, сохраняя единственность владельца.

## Критерии приёмки

Два реальных телефона: вызов, согласие, синхронный старт, движения обоих, убывание, единый победитель и одинаковый результат в истории после перезапуска. Проверить выход, denied sensors, сворачивание, авиарежим, reconnect, повтор пакетов/POST, просроченный билет, чужой battleId, одинаковые seq, поддельные 100%, одновременный финиш, сбой БД в финале и перезапуск владельца. Ни один повтор не начисляет очки второй раз. Витрина не принимает 4-й/невыданный/повторный стикер.

Тесты Go: unit rules (общие fixtures с TS), go test -race, транзакционные интеграционные с PostgreSQL, WebSocket с двумя клиентами и управляемыми часами, нагрузочный тест комнат с измерением памяти/очередей. При медленном клиенте очередь ограничить: промежуточные snapshots объединять, финал не терять — получать через GET после reconnect. Цель MVP: доставка snapshot p95 <250 ms при RTT 100 ms; бюджет нагрузки указывать вместе с железом и числом комнат, а не обещать без измерения.

Наблюдаемость: активные комнаты/сокеты, длина очередей, tick lag, p95 доставки, reconnect, rejected strokes, дубли финала, задержка outbox. Логи структурные requestId/battleId, без токенов и сырых персональных данных. Передача разработчику: OpenAPI, AsyncAPI, миграции, seed-каталог, правила с fixtures, docker compose, инструкция запуска и отчёт тестов.
